### 0.2 订单状态机（`trx_order.order_status`）【已验证】

| 值 | 含义 | 允许的前置状态 → 操作 |
|---|---|---|
| 0 | 待付款 | 提交订单即落此态；可取消、可支付 |
| 1 | 已支付/待发货 | 仅由 0 支付成功进入；可发货、可申请售后 |
| 2 | 已发货/待收货 | 仅由 1 发货进入；可完成、可申请售后 |
| 3 | 已完成 | 仅由 2 完成进入；可申请售后、后台可发起退款 |
| 4 | 已关闭 | 仅由 0 取消，或退款成功关闭 |
| 5 | 售后中 | 会员申请售后进入；驳回恢复原状态，退款成功转 4 |

> 状态推进均通过 `TryTransitionAsync` 的条件更新（`WHERE id=? AND order_status=期望值`）实现【已验证，OrderService.cs#L1746-L1752】。

### 2.1 已确认“通过”的防御点（避免误判为缺陷）

1. **发货/完成/取消/支付** 均使用 `UPDATE ... WHERE id=? AND order_status=期望值` 状态抢占，重复点击只成功一次【已验证】。
2. **支付链路**：订单状态、库存扣减、`log_stock_log`、应收结清、会员累计消费、余额冻结释放均在**同一事务**内【已验证】。
3. **N+1**：列表页不存在“20 条订单循环 20 次查买家/明细”的写法；买家名与明细汇总均批量查询【已验证】。
4. **商品快照**：`trx_order_item` 保存下单时的商品名、SKU 名、规格、图片、单价；商品改名/删除不影响历史订单【已验证】。
5. **物流默认超时**：`HttpClient.Timeout=10s`，全链路 `async/await`，不会因外部慢响应阻塞线程池线程【已验证】。

## 三、程序设计合理性评估（架构建议）

### 3.1 物流模块：解耦与异步化（当前得分：中）

| 维度 | 现状【已验证】 | 评估 |
|---|---|---|
| 缓存 | `IMemoryCache`，60 分钟，key=`logistics:{单号}` | 有缓存但仅进程内，多实例部署命中率骤降；key 设计有串数据风险 |
| 刷新 | 无刷新接口，前端按钮无法绕过缓存 | 缓存“只能等过期”，退件/改单场景不可用 |
| 调用方式 | 请求线程内同步等待第三方（识别+轨迹最多两次外呼） | 外部依赖直接压在用户请求时延上，无异步化 |
| 失败处理 | try-catch + 1 次超时重试；失败写日志 | 无熔断/退避/限流；5xx 不重试 |
| 推送 | 无快递100 订阅/快递鸟推送 | 只能“用户点了才查”，无法主动更新轨迹 |
| 日志 | 同步写 `logistics_query_log`，命中缓存不写 | 审计断链 + 请求尾延迟 |

**目标架构（建议）**：
1. 查询接口只读内部 `logistics_track` 表/Redis；首次未命中时入队异步拉取，立即返回“查询中”；前端轮询或 SSE。
2. 定时任务对“未签收”运单批量轮询（按承运商配额分片），或接入快递100 订阅推送，落库即更新。
3. Redis 缓存 key = `carrier:tracking`，TTL 分级（已签收 24h / 运输中 30min），并提供 `refresh` 权限的强制刷新。
4. 外部调用统一封装：连接超时 2s、读超时 8s、指数退避 2 次、熔断（连续失败 N 次打开 60s）、按用户/IP 令牌桶限流。
5. 查询日志异步落库（消息队列/后台任务），失败/成功都记录，保留 90 天归档。

### 3.2 订单快照与只读性（当前得分：良）

- `trx_order_item` 已冗余 `prod_name / sku_name / spec_info / product_image / unit_price`，`trx_order` 保存 `pay_amount / freight / discount` 与收货信息【已验证】。
- 待补强：①退款单/退货单展示仍关联实时商品表取图与名（若商品删除需兜底快照）；②支付流水缺少“费率/渠道”快照；③建议增加 `order_status_history`（操作人、前后状态、时间），当前状态变更只依赖业务日志表，追溯粒度不足。
- 结论：**快照设计方向正确**，无需重构表结构，只需补齐售后侧与状态历史。

### 3.3 分页与百万级订单（当前得分：差 → 需改造）

现状：`Skip((page-1)*size).Take(size)` + 每页 `Count(*)`，排序 `id DESC`，时间/状态/关键词组合无复合索引【已验证】。

建议按优先级实施：
1. **复合索引**（先解决 80% 慢查询）：
```sql
-- 状态 + 时间 + 主键（覆盖后台按状态筛选并按时间/ID 倒序）
CREATE INDEX idx_trx_order_status_create_id ON trx_order (order_status, create_time, id);
-- 时间 + 主键（覆盖“过去一年”并按游标翻页）
CREATE INDEX idx_trx_order_create_id        ON trx_order (create_time, id);
-- 买家 + 时间 + 主键（会员端“我的订单”）
CREATE INDEX idx_trx_order_buyer_create_id  ON trx_order (buyer_id, create_time, id);
```
> 说明：MySQL 8.0 无 `CREATE INDEX IF NOT EXISTS`，先查 `information_schema.statistics` 再执行；新增 `(create_time,id)` 后原 `idx_create_time` 可评估删除。
2. **游标分页**：列表接口改为 `lastId`（或 `lastCreateTime+lastId`）游标，SQL 变为 `WHERE id < @lastId ORDER BY id DESC LIMIT 20`，彻底消除深翻页；`total` 改为“是否还有下一页”或缓存计数，避免每次 `COUNT(*)`。
3. **搜索分离**：订单号/手机号/收货人使用前缀匹配或独立检索（ES）；当前 `LIKE '%kw%'` 在百万级必然全表。
4. **导出异步化**：提交任务→后台生成→对象存储下载；避免同步 5000 行 NPOI。
5. **只读库/分区**：订单按年分区或历史归档库，后台默认查近 12 个月。

### 3.4 状态机与资金一致性（当前得分：中）

- 建议把状态转换集中为一张**显式转换表**（From → To + 守卫条件 + 所需权限），所有入口复用同一个 `Transition(orderId, from, to)`，避免“支付/取消/退款/退货”四条链路各写一套判断。
- 退款补**幂等键**：`trx_refund` 增加条件更新占位；`mkt_balance_log(related_type, related_id, change_type)` 唯一索引，重复打款直接冲突回滚。
- 售后链路补**终态收敛**：退款单 → 已退款时统一关闭订单；退货拒收时恢复订单原状态（当前仅退款驳回会恢复，退货拒收路径未恢复订单）。
- 建议增加 T+1 **资金对账任务**：订单实付 vs 余额扣减流水 vs 退款流水，三方勾稽差异告警。
