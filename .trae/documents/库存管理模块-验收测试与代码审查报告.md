**三个必须先点明的需求偏差（事实）：**

1. **出库类型只有 1-样品领用 / 2-报损 / 3-其他**（校验见 [StockOutService.cs](file:///f:/WorkSpace/Jsd/Jsd.Api/Services/StockOutService.cs#L377-L383)，建表注释见 [Jsd_order.sql](file:///f:/WorkSpace/Jsd/Jsd.Api/sql/scripts/Jsd_order.sql#L388-L402)）。**没有“销售出库”，也没有“采购退货出库”**。销售扣库存只发生在订单支付链路（`OrderService.DeductStockAsync`）。
2. **“入库管理”的手工入库（stockIn）不绑定采购订单**。`StockInCreateDto` 只有供应商 + 商品/SKU + 数量 + 成本价，无 `orderId`；因此手工采购入库**无法做超收校验**，只能“想入多少入多少”。真正绑订单、能拦超收的是采购模块的 `pur_inbound`（`/api/inbound`）。
3. **“多仓库 SKU 实时库存”不成立**：库存只有 `prod_sku.stock` 单列（[ProdSku.cs](file:///f:/WorkSpace/Jsd/Jsd.Api/Entities/ProdSku.cs#L55-L57)），`pur_inbound.warehouse_id` 仅作引用存储，实体注释明确“本系统当前无仓库主数据表（多仓库为待建功能）”（[PurInbound.cs](file:///f:/WorkSpace/Jsd/Jsd.Api/Entities/PurInbound.cs#L13-L14)）。没有 `product_warehouse_stock` 中间表。
4. **预警只有“最低阈值”**：`log_stock_warning` 只有 `warning_stock`（低于/等于则报警），**没有最高库存阈值**（[LogStockWarning.cs](file:///f:/WorkSpace/Jsd/Jsd.Api/Entities/LogStockWarning.cs#L33-L35)）。

> - **出库**：不会超卖。`StockOutService.AdjustStockAndLogAsync` 是“读当前值 + 条件更新 `WHERE id=? AND stock=当前值`”的 CAS（[L458-L481](file:///f:/WorkSpace/Jsd/Jsd.Api/Services/StockOutService.cs#L458-L481)），并预判 `after<0`（L452-L456），扣减结果是原子写入。
> - **但出库存在“误报失败”的可用性问题**：重试发生在**同一事务内**，MySQL REPEATABLE READ 下重复 SELECT 仍读事务快照，CAS 会连续失败 3 次后抛“库存更新并发冲突”（【推断】取决于隔离级别与驱动，需实测）。
> - **入库（手工 stockIn / 采购 pur_inbound）会丢更新**：走 EF 跟踪实体 `sku.Stock = before + qty` 后 `SaveChanges`（[StockInService.cs L434-L447](file:///f:/WorkSpace/Jsd/Jsd.Api/Services/StockInService.cs#L434-L447)、[InboundService.cs L459-L471](file:///f:/WorkSpace/Jsd/Jsd.Api/Services/InboundService.cs#L459-L471)），生成的是**绝对赋值 UPDATE**，无并发令牌/无锁。两人同时入库各 +5，库存只 +5，但两条日志都记 +5 → 账实不符。**这是本模块最隐蔽的致命缺陷。**

## 三、架构设计优化建议

### 3.1 出入库记录的可追溯性（StockLog）

**现状（事实）**：`log_stock_log` 有 `ref_type + ref_id + change_qty + before/after + operator`（[LogStockLog.cs](file:///f:/WorkSpace/Jsd/Jsd.Api/Entities/LogStockLog.cs#L43-L50)），可追溯到单据主键；但：
- 手工入库 **删除**时不写冲销流水（RC-06）；
- 手工入库备注固定“采购入库”，不落单号（[StockInService.cs L452-L470](file:///f:/WorkSpace/Jsd/Jsd.Api/Services/StockInService.cs#L452-L470)），要靠 `ref_id` JOIN 才能拿到 `stock_in_no`；
- 没有 `stock_in_no / stock_out_no / order_no / batch_no` 冗余列，追溯必须跨表 JOIN；
- 批次号 `batch_no` 只存在 `pur_inbound_item`（[PurInboundItem.cs L36-L39](file:///f:/WorkSpace/Jsd/Jsd.Api/Entities/PurInboundItem.cs#L36-L39)），**未写入库存流水**，无法按批次追踪库龄/召回。

**建议（按性价比排序）**：
1. **补全流水闭环**：所有删除/冲销必须写反向流水，`ref_type` 统一枚举（`stock_in / stock_in_update / stock_in_delete / stock_out / stock_out_update / stock_out_delete / pur_inbound / check / check_update / order`），禁止物理删除日志（删除单据只删单据，流水永久保留）。
2. **流水加冗余业务单号 + 批次号**：`ref_no VARCHAR(32)`、`batch_no VARCHAR(32)`，让“某批货为什么数量不对”一次查询即可回答，无需 JOIN。
3. **加“库存快照余额”列**：`after_stock` 已有；建议增加日终结算表 `log_stock_balance_daily(sku_id, stat_date, qty)`，支撑对账与趋势。
4. **追溯链**：订单支付流水（`change_type=4, ref_id=order_id`）→ 应收/收款 → 出库；建议在 `ref_type` 上约定“库存动作 → 业务单据”的单一职责，避免同一动作多种 ref_type 混用。
5. **索引**：`(sku_id, create_time)`、`(ref_type, ref_id)`、`(prod_info_id, create_time)`，见 3.5。

### 3.2 预警阈值的触发方式与性能

**现状（事实）**：完全**查询时实时计算**，无事件、无队列、无定时任务：
- 预警页：SQL 相关子查询（[StockWarningRepository.cs L44-L58](file:///f:/WorkSpace/Jsd/Jsd.Api/Repositories/StockWarningRepository.cs#L44-L58)）；
- 库存查询页：内存计算（[StockQueryService.cs L105-L118](file:///f:/WorkSpace/Jsd/Jsd.Api/Services/StockQueryService.cs#L105-L118)）；
- 首页看板：原生 SQL 全表 `GROUP BY prod_info_id` 聚合（[DashboardService.cs L273-L298](file:///f:/WorkSpace/Jsd/Jsd.Api/Services/DashboardService.cs#L273-L298)）。
- 只有最低阈值，无最高阈值。

**评价**：查询时计算的好处是**永不失真**（改了阈值即时生效），坏处是**每次库存变动都不触发任何逻辑**，只能“人打开页面才看到”；同时首页/明细存在全量扫描（RC-14/15）。

**建议（推荐分层）**：
1. **写路径埋点（同步轻量，不查阈值）**：库存变动成功后，把 `(sku_id, 新库存)` 写入一张 `stock_change_event` 表（或 Redis Stream / 消息队列），**不在事务内做阈值比较**，避免拖慢入库出库主链路。
2. **异步消费者**：定时/队列批量比对 `log_stock_warning`（含最低/最高阈值），生成 `stock_warning_event`（去重键：`sku_id + 阈值类型 + 状态`），驱动站内信/飞书/邮件。仅在“状态由正常→预警”时发一次，恢复时发“解除”，避免每笔变动重复告警。
3. **页面读取预计算状态**：`stock_warning_event` 存当前预警状态，预警页直接分页查事件表（可走索引），**不再逐行子查询**。
4. **补最高库存阈值**：`log_stock_warning` 增加 `max_stock`（可空），判定 `stock >= max_stock` 触发“积压预警”；唯一约束 `(prod_info_id, sku_id)`（注意 `sku_id NULL` 的唯一性在 MySQL 中需用生成列或应用层保证）。
5. **性能兜底**：即使保留实时计算，也应把预警状态改为“变动时增量维护”，而不是全量载入内存。

### 3.3 多仓库扩展性

**现状（事实）**：**单仓模型**。
- 库存只有 `prod_sku.stock`（[ProdSku.cs L55-L57](file:///f:/WorkSpace/Jsd/Jsd.Api/Entities/ProdSku.cs#L55-L57)）；
- `pur_inbound.warehouse_id` 是“引用存储”，无仓库主表、无校验（[PurInbound.cs L13-L14](file:///f:/WorkSpace/Jsd/Jsd.Api/Entities/PurInbound.cs#L13-L14)）；
- 手工入库/出库/盘点/订单扣减全都没有仓库维度；
- 因此“多仓库 SKU 实时库存明细”在当前版本**无法验收**。

**建议（演进路径，避免大爆炸改造）**：
1. **新增仓库主数据**：`inv_warehouse(id, code, name, status)`。
2. **新增库存中间表**：`inv_warehouse_stock(warehouse_id, sku_id, stock, version)`，主键/唯一键 `(warehouse_id, sku_id)`；`prod_sku.stock` 降级为“全仓汇总冗余”（可由汇总表维护，或改为视图/异步汇总，避免双写不一致）。
3. **单据增加仓库维度**：入库/出库/盘点/订单明细统一加 `warehouse_id`（出库来源仓、入库目标仓、调拨单）。
4. **所有库存写入改为按 `(warehouse_id, sku_id)` 原子更新**：`UPDATE inv_warehouse_stock SET stock=stock-? WHERE warehouse_id=? AND sku_id=? AND stock>=?`，配合唯一键。
5. **索引**：`inv_warehouse_stock` 至少 `UNIQUE(warehouse_id, sku_id)` + `KEY(sku_id)`；所有跨仓汇总查询按 `sku_id` 走索引，禁止全表 GROUP BY。
6. **迁移策略**：历史数据回填到默认仓（`warehouse_id=1`），`prod_sku.stock` 保留只读兼容一段时间，待全部链路切换后下线。
7. **调拨**：多仓必须有 `inv_transfer` 单（转出/转入同一事务、双仓原子更新），否则库存会“凭空出现/消失”。

> 若短期不做多仓，也应**删除或明确标注 `warehouse_id` 为占位字段**，避免前端误以为支持多仓（当前查询接口甚至没有 `warehouseId` 过滤，见 [StockQueryController.cs L57-L69](file:///f:/WorkSpace/Jsd/Jsd.Api/Controllers/StockQueryController.cs#L57-L69)）。

### 3.4 权限与审计（安全架构）

1. 五个库存 Controller 全部补齐 `[Permission]`（RC-05），并统一权限码（RC-07），与 `sys_menu` 种子对齐后再授权角色。
2. **写操作强制落操作人**：目前 `operator` 直接取前端传入（如 `dto.Operator`，[StockOutCreateDto.cs L24-L26](file:///f:/WorkSpace/Jsd/Jsd.Api/Models/StockOut/StockOutCreateDto.cs#L24-L26)），可伪造。建议统一取 `CurrentUserService`，前端只读展示。
3. **审计不可物理删除**：入库/出库/盘点单建议软删除（`is_deleted` + `delete_time`），流水永不删除，满足追溯与合规。

   - 创建盘点（系统 100）→ 出库 10 → 实盘 90 → 完成；
   - 断言：最终库存 = 90（当前实现会得到 80）。
5. **权限回归（RC-05）**
   - 用无 `stock_in:add` 角色调用 5 个写接口，断言 403（当前会成功，可证明风险存在）。
6. **预警验收**
   - 阈值 10、库存 11 → 出库 2 → `GET /api/stockWarning?onlyWarning=true` 应包含该 SKU，`isWarning=true`。
7. **静态一致性**
   - `dotnet build Jsd.Api.csproj` 保证改动可编译；接口回归覆盖 UAT 表中 P0 用例。

## 五、结论摘要

- **防超卖**：出库与订单支付已有 CAS 条件更新，**不会超卖**；但入库侧缺少并发保护，**会丢更新**（不易察觉、危害更大）。
- **事务一致性**：库存变动与单据状态变更基本在同一 `IDbContextTransaction` 内；真正的问题是**状态前置校验在事务外**，形成 TOCTOU，导致重复确认（库存/应付双记）与重复盘点调整。
- **原子性**：出库/盘点用了条件更新，具备原子性；入库仍是“读-改-写”绝对赋值，**不原子**。
- **可追溯性**：流水字段足够（`ref_type/ref_id`），但删除无冲销、无单号/批次冗余、无复合索引，追溯体验不达标。
- **预警**：查询时实时计算，页面能正确展示，但**无主动通知、无最高阈值、查询成本随数据量上升**。
- **多仓库**：**未实现**，`warehouse_id` 只是占位字段，库存仍是 `prod_sku.stock` 单列。
- **安全**：库存模块写接口**未做按钮级权限硬校验**，是本次验收最高优先级的安全缺陷。
