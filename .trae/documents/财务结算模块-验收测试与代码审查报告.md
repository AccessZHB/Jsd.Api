## 二、代码审查风险清单

### 🔴 P0 — 必须立即修复

#### P0-1 全部财务 Controller **零权限控制**（资金敞口）
- 位置：[ReceivableController.cs](file:///f:/WorkSpace/Jsd/Jsd.Api/Controllers/ReceivableController.cs)、[PaymentController.cs](file:///f:/WorkSpace/Jsd/Jsd.Api/Controllers/PaymentController.cs)、[InvoiceController.cs](file:///f:/WorkSpace/Jsd/Jsd.Api/Controllers/InvoiceController.cs)、[ReconciliationController.cs](file:///f:/WorkSpace/Jsd/Jsd.Api/Controllers/ReconciliationController.cs)
- 事实：4 个控制器只有 `[Authorize]`，**没有任何 `[Permission]` 特性**。权限常量已定义（`finance:payment:add/verify`、`finance:invoice:apply/issue/cancel`、`finance:reconciliation:download/run/handle`、`finance:receivable:list`）却完全未挂载。`PaymentController` 类注释里甚至写明了权限码却没应用。
- 影响：**任何登录账号（含客服、仓库）都能录入收款、核销账单、开票/作废/红冲、处理对账差异**，直接触碰资金与税务凭证。
- 修复：所有资金写 Action 补 `[Permission]`；`SyncFromOrder` 作为内部触发端点应移除 HTTP 暴露或加 `finance:receivable:sync` 并限制财务角色。

#### P0-2 核销（WriteOff）**无行锁/乐观锁 → 并发可重复核销**
- 位置：[PaymentService.cs#L177-L313](file:///f:/WorkSpace/Jsd/Jsd.Api/Services/PaymentService.cs#L177-L313)
- 事实：
  1. `payment.Status != Pending` 是「先查后判」，无 `FOR UPDATE` / 条件更新；
  2. `receivable.UnpaidAmount` 检查后 `PaidAmount += offset` 是典型「读-改-写」丢失更新；
  3. `mkt_payment_item` 表**没有唯一索引** `(payment_id, receivable_id)`（[Jsd_order.sql#L1026-L1028](file:///f:/WorkSpace/Jsd/Jsd.Api/sql/scripts/Jsd_order.sql#L1026-L1028)），同一 (收款, 应收) 可被插入多行。
- 场景：两个财务/两个请求同时核销同一笔收款单，两者都读到 `status=Pending`、`unpaid=3000`，都插入明细、都扣减应收 → **同一笔钱核销两次**，资金对账直接出错。
- 修复：
  - 事务内对收款单和涉及的应收单加 `FOR UPDATE`（`FromSqlRaw("SELECT ... FOR UPDATE")` 或 EF Core 8 `ForUpdate`）；
  - 或用 `ExecuteUpdateAsync` 条件更新抢占：`UPDATE mkt_payment SET status=1 WHERE id=? AND status=0`，`claimed==0` 则回滚；
  - 给 `mkt_payment_item` 加唯一约束 `uk_payment_receivable (payment_id, receivable_id)`，作为 DB 兜底。

#### P0-3 开票申请（ApplyInvoice）**无事务、无唯一约束 → 并发重复开票**
- 位置：[InvoiceService.cs#L199-L311](file:///f:/WorkSpace/Jsd/Jsd.Api/Services/InvoiceService.cs#L199-L311)
- 事实：
  1. 查重 `FirstOrDefaultAsync(Status != Canceled)` 后直接 `AddAsync + SaveChangesAsync`，**无事务包裹**；
  2. `order_invoice` 表只有 `uk_invoice_no`，**没有**「同一订单只能有一张有效票」的唯一约束（[invoice_align.sql#L67-L73](file:///f:/WorkSpace/Jsd/Jsd.Api/sql/scripts/invoice_align.sql#L67-L73)）；
  3. 第三方开票平台调用 `TryIssueByPlatformAsync` 在第一次 SaveChanges 之后，若平台成功但进程崩溃，记录停在「申请中」且无法重提（被查重拦截）。
- 场景：用户双击「申请开票」，两个并发请求都通过查重 → 生成两张申请中发票；若对接了第三方平台，可能**重复向税局/百望提交开票**，造成税务事故。
- 修复：
  - 查重 + 插入放入显式事务；
  - 增加 DB 唯一约束保证单订单一张有效票（MySQL 可用生成列或应用层 `(order_id, status)` 的部分索引替代方案：加 `active_order` 列，active=1 时唯一，作废置 NULL）；
  - 平台调用失败不阻断申请（已实现降级），但应在申请记录上记录 `platform_request_id` 做幂等，防止平台侧重复开票。

### 🟠 P1 — 高风险

#### P1-1 发票回写/作废「先查后写」无抢占

#### P1-2 `SyncFromOrderAsync` 生成应收无唯一约束兜底

- 修复：加 `UNIQUE KEY uk_order_id (order_id)`；同步方法用 `INSERT ... ON DUPLICATE KEY` 或 `ExecuteUpdate` 抢占。

#### P1-3 `SettleByOrderAsync` 结清应收无事务、无并发保护

#### P1-4 对账差异处理无权限、无状态校验

## 三、架构设计优化建议

### 3.1 流水表 Append-Only 与追溯
- 现状：`mkt_payment_item`、`trx_payment_log`、`mkt_balance_log` 均为只追加，符合财务流水设计原则 ✅。
- `trx_receivable`、`mkt_payment` 是「余额/状态汇总表」，允许 UPDATE（paid/unpaid/status），这是合理的——它们不是流水而是账本余额。
- 建议：给 `mkt_payment_item` 增加唯一约束 `uk_payment_receivable`，防止重复核销明细；给 `order_invoice` 增加「单订单有效票唯一」约束，防止重复开票。

### 3.2 高并发资金操作的行级锁 / 乐观锁
- 核销、结清、开票状态流转全部改用「条件更新抢占」模式：
  ```sql
  UPDATE mkt_payment SET status=1 WHERE id=? AND status=0;   -- claimed==0 → 已被他人处理
  UPDATE trx_receivable SET unpaid=unpaid-?, paid=paid+? WHERE id=? AND unpaid>=?;
  UPDATE order_invoice SET status=1 WHERE id=? AND status=0;
  ```
- 对必须读-改-写的场景（如批量核销计算），事务内用 `SELECT ... FOR UPDATE` 锁定收款单和应收行。
- 核销加幂等键：前端传 `requestId`，后端 `IMemoryCache` 短时去重，防双击。

### 3.3 权限模型
- 立即挂载 `[Permission]`，并按角色分发：
  - 财务(4)：收款 add/verify、发票 apply/issue/cancel、对账 download/run/handle
  - 运营(2)/仓库(3)：仅 list
  - 超管：IsSuper 放行
- 同步 `sys_menu` / `sys_role_menu` 种子（[invoice_reconciliation_menu.sql](file:///f:/WorkSpace/Jsd/Jsd.Api/sql/scripts/invoice_reconciliation_menu.sql) 已定义 325~334，需确认已入库并授权）。

### 3.4 第三方开票幂等
- `InvoiceService.ApplyInvoiceAsync` 应在调用第三方平台前生成 `platform_request_id`（如 `INV-{invoiceId}-{timestamp}`），写入申请记录。平台调用带上该 ID，平台侧据此幂等；若本地记录已有成功的 `invoice_no`，直接返回不再调平台。
- 申请记录 + 平台调用结果回写应在同一事务，避免「平台成功、本地仍是申请中」。

### 3.5 对账增强
- `reconciliation_check` 差异表虽非流水，但建议加 `(bill_id, out_trade_no)` 唯一约束，配合 `INSERT ... ON DUPLICATE KEY UPDATE` 替代「先删后插」，减少高并发对账的表锁。
- 系统侧时间口径目前用 `payment_order.create_time`（非支付成功时间），建议新增 `pay_time` 字段并在支付成功时回填，对账时间窗口更精准。

### 3.6 价税分离校验
- 发票申请时若传 `tax_amount`，应校验 `tax_amount < total_amount` 且 `不含税金额 + tax_amount == total_amount`（允许 0.01 尾差），避免票面与税务系统比对失败。
