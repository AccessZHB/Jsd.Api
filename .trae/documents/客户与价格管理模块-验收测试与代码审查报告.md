## 二、代码审查风险清单

### 🔴 P0 — 必须立即修复

#### P0-1 价格策略 / 客户等级 全部高危写接口 **零权限控制**
- 位置：[PriceStrategyController.cs](file:///f:/WorkSpace/Jsd/Jsd.Api/Controllers/PriceStrategyController.cs)、[MemberLevelController.cs](file:///f:/WorkSpace/Jsd/Jsd.Api/Controllers/MemberLevelController.cs)、[PriceController.cs](file:///f:/WorkSpace/Jsd/Jsd.Api/Controllers/PriceController.cs)、[OrderPriceSnapshotController.cs](file:///f:/WorkSpace/Jsd/Jsd.Api/Controllers/OrderPriceSnapshotController.cs)
- 事实：4 个控制器只有 `[Authorize]`，**没有任何 `[Permission]` 特性**。而 [PriceEnums.cs#L307-L328](file:///f:/WorkSpace/Jsd/Jsd.Api/Models/Price/PriceEnums.cs#L307-L328) 已定义了完整权限常量（`price:strategy:*`、`price:level:*`、`price:change-log:list`、`price:snapshot:*`），却未挂到 Action 上。
- 影响：**任何登录后台账号（含运营专员、仓库管理员）都能新增/修改/启用/停用价格策略、改客户等级折扣、改价**，直接触碰资金。这是资金安全致命漏洞。
- 同时 `POST /api/order-price-snapshots/batch`（[OrderPriceSnapshotController.cs#L38-L42](file:///f:/WorkSpace/Jsd/Jsd.Api/Controllers/OrderPriceSnapshotController.cs#L38-L42)）是内部写快照接口，却以公开 HTTP 暴露且无权限，任意登录用户可**伪造历史价格快照**，污染审计与毛利数据。
- 修复：所有写 Action 补 `[Permission(PricePermissions.Xxx)]`；`SaveBatch` 改为仅供 `OrderService` 内部调用（移除 HTTP 路由，或加 `[SuperAdminOnly]` + `price:snapshot:write` 权限，并增加幂等校验 `order_id` 唯一约束）。

#### P0-2 `price_rule.calc_value` 精度错误：折扣率被截断到 2 位小数
- 位置：[price_balance_module.sql#L84](file:///f:/WorkSpace/Jsd/Jsd.Api/sql/scripts/price_balance_module.sql#L84) `calc_value DECIMAL(10,2)`；[PriceRule.cs#L49](file:///f:/WorkSpace/Jsd/Jsd.Api/Entities/PriceRule.cs#L49) `TypeName = "decimal(10,2)"`
- 事实：`calc_value` 字段是多态的——固定价（元，2 位）、折扣率（0.8500，需 4 位）、减免金额（元，2 位）。代码 [PriceService.cs#L1282-L1286](file:///f:/WorkSpace/Jsd/Jsd.Api/Services/PriceService.cs#L1282-L1286) 用 `decimal.Round(input.CalcValue, 4)` 保留 4 位，但数据库只存 2 位，折扣率 `0.8765` 会被存成 `0.88`，造成 0.35% 的价差。
- 对比：`mem_member_level.default_discount` 是 `DECIMAL(5,4)`，`price_rule_item.discount` 也是 `DECIMAL(5,4)`，唯独规则主表的 `calc_value` 是 `(10,2)`，三者不一致。
- 影响：财务对账会出现分级误差，且「阶梯价用 item.discount（4位）、非阶梯用 rule.calc_value（2位）」同一会员同商品在不同数量下折扣精度跳变。
- 修复：`ALTER TABLE price_rule MODIFY calc_value DECIMAL(10,4)`；Entity `TypeName` 同步改为 `decimal(10,4)`。

### 🟠 P1 — 高风险

#### P1-1 价格策略变更 **无乐观锁 / 无防重复提交**
- 位置：`UpdateStrategyAsync`、`SubmitStrategyAsync`、`SaveRulesBatchAsync`、`DisableStrategyAsync`
- 事实：均采用「读 tracked 实体 → 改字段 → SaveChanges」，没有 `RowVersion`/并发令牌，也没有基于 `status` 的条件更新（`ExecuteUpdateAsync ... WHERE status=Draft`）。
- 场景：管理员双击「提交启用」或两人同时编辑同一草稿策略，两个请求都读到 `status=Draft`，都通过校验并 SaveChanges，可能产生**重复的变更日志**、规则全量覆盖互相覆盖、或「状态已被对方改为启用后，本方仍按草稿写入」。
- 修复：状态流转用 `ExecuteUpdateAsync(...).Where(s => s.Id == id && s.Status == (int)StrategyStatus.Draft)` 抢占；`SaveRulesBatch` 在事务内重查策略状态并加条件更新。

#### P1-2 取价引擎每次请求**全量加载所有生效策略 + 规则 + 明细**，无缓存
- 位置：[PriceService.cs#L709-L724](file:///f:/WorkSpace/Jsd/Jsd.Api/Services/PriceService.cs#L709-L724)
- 事实：`QuotationAsync` 每次都查 `GetEffectiveStrategiesAsync` + 所有 rules + 所有 items。商品列表 [ProdInfoService.ApplyMemberPriceAsync](file:///f:/WorkSpace/Jsd/Jsd.Api/Services/ProdInfoService.cs#L144-L211) 每翻一页就调用一次取价。项目内其他模块（字典、系统配置、物流、验证码）都有 `IMemoryCache`，唯独价格策略**无任何缓存**。
- 影响：价格是高频读数据，每次列表页/详情页/下单都查 3 张表，QPS 上来后 DB 压力集中在 `price_strategy` / `price_rule` / `price_rule_item`。
- 修复：加进程内缓存（key 例如 `price:strategies:effective`），策略/规则/等级任何写操作后统一清除。多实例部署时换 Redis（与字典缓存同套路）。

#### P1-3 `POST /api/price/quotation` **越权**：可传任意会员ID取价
- 位置：[PriceController.cs#L32-L47](file:///f:/WorkSpace/Jsd/Jsd.Api/Controllers/PriceController.cs#L32-L47)
- 事实：取价接口的 `MemMemberId` 来自请求体，不校验调用者与该会员的归属关系。任何后台账号可枚举会员ID，拿到其他客户的**专属价、等级折扣**等敏感定价信息。
- 修复：若接口仅供后台客服代客报价，加 `price:quotation` 权限并记操作日志；若仅内部下单用，改为不对外暴露的内部方法（`OrderService` 已直接调 `_priceService.QuotationAsync`，HTTP 端点可删除）。

#### P1-4 `price_change_log` 缺失 **关联商品/SKU 维度**
- 位置：[PriceChangeLog.cs](file:///f:/WorkSpace/Jsd/Jsd.Api/Entities/PriceChangeLog.cs)
- 事实：日志只记录到 `strategy_id` / `rule_id` / `field_name`。当规则 `apply_scope=Material`（指定商品）或阶梯价明细改价时，日志里**看不到是哪个 SKU 的价变了**，需要再 join `price_rule_item` 反查，审计体验差且无法直接按商品追溯。
- 修复：改价类日志（尤其 `price_rule_item.price/discount/reduce_amount` 变化）补充 `material_id` / `prod_info_id` 字段。

### 🟡 P2 — 中风险

#### P2-1 `SaveRulesBatchAsync` 新规则先 `SaveChanges` 拿 ID，**非纯单事务落库**
- 位置：[PriceService.cs#L563-L568](file:///f:/WorkSpace/Jsd/Jsd.Api/Services/PriceService.cs#L563-L568)

#### P2-3 商品列表会员价计算有**静默吞异常**

#### P2-4 `QuotationAsync` 抛 `InvalidOperationException`（英文）直接回前端

## 三、架构设计优化建议

### 3.1 缓存架构（P0 级性能/一致性）
现状：价格策略**零缓存**，每次取价扫 3 表。
建议：
1. 引入 `IPriceCache`（默认 `IMemoryCache`，多实例换 Redis），缓存粒度：
   - `price:effective:strategies` → 生效策略 + 规则 + 明细的**整体快照**（取价时一次性反序列化，避免逐对象查询）；
   - `price:level:{id}` → 等级默认折扣；
2. 失效策略：所有写操作（策略增删改/启停、规则批量保存、等级增删改/启停）统一调用 `_priceCache.InvalidateAsync()`；
3. 会员的等级变更也需触发缓存清理（当前等级即时生效靠每次查库，缓存后必须失效）。

### 3.2 订单快照原子性
现状：**已在同一事务内**，符合要求。
补强建议：
1. 给 `order_price_snapshot.trx_order_id` 加索引（若未加），快照列表按订单查询走索引；
2. 考虑加唯一约束 `(trx_order_id, trx_order_item_id)`，防止重复写入；
3. `POST /api/order-price-snapshots/batch` 公开端点应**移除或限制为内部调用**，避免外部伪造快照。

### 3.3 权限与审计
1. 立即给 4 个控制器补 `[Permission]`，权限常量已存在（`PricePermissions`），只需挂载 + `sys_menu` 种子同步；
2. 价格策略/规则的写操作建议额外要求「财务」角色（参考本次售后权限分发策略），运营/仓库只给 `list` 权限；
3. `quotation` 接口如保留对外，加 `price:quotation` 权限 + 操作日志。

### 3.4 精度统一
1. `price_rule.calc_value` 统一为 `DECIMAL(10,4)`（同时支持 2 位金额和 4 位折扣率）；
2. 代码层所有金额 `Round(.,2)`、所有折扣率 `Round(.,4)`，与 DB 列精度一一对应，避免「代码 4 位、库 2 位」的静默截断；
3. 建表脚本与实体 `TypeName` 必须同源，建议加启动时 EF 列精度自检。

### 3.5 并发与幂等
1. 状态流转（草稿→启用→停用）改用 `ExecuteUpdateAsync` 条件更新抢占；
2. 「提交启用」「批量保存规则」加幂等键（前端传 `requestId`，后端用 `IMemoryCache` 短时去重），防双击；
3. `price_change_log` 增加 `request_id` 字段，同一请求的多次字段变更可聚合展示。

### 3.6 取价引擎可观测性
1. `QuotationAsync` 增加 `trace_id`，把「命中/未命中每层策略」的决策链路写入 debug 日志或返回 `discount_info`，便于客服解释「为什么这个客户是这个价」；
2. 取价异常不要静默吞（P2-3），至少 `LogWarning` 带 memberId + skuIds。
